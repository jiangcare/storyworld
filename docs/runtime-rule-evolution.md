这不是一个等待玩家提问并回答的 AI 聊天游戏。它是一部由游戏世界持续驱动、由 AI 实时写作、玩家可以随时介入并改变走向的可游玩小说。

# 游戏过程中的规则补全

2026-09-10。设计规格，尚未实现。承接 [生成式文字世界](generative-world-design.md)：允许玩家的尝试暴露原先未定义的机制，由 AI 提出受约束的规则补全；不能把“规则固定”理解为必须预先写完每部功法和每种能力组合。

核心原则：**新内容可以带来新规则；新规则必须有适用范围、可执行含义和持续记忆，不能临场编造胜负。** 运行时扩展的是可验证的规则数据，不是让模型编辑源代码或执行任意脚本。

## 哪些可以补，哪些不能改

| 层级 | 示例 | 生效方式 |
| --- | --- | --- |
| 引擎基础约束 | 状态写入权限、事务、资源非负、随机记录、玩家授权、事件去重 | AI 无权改写；新增底层执行能力走代码开发与测试 |
| 世界基本法则 | 境界体系、复活模式、力量上限、资源来源、同类能力的公共结算方式 | 开局建立并版本化；不能在一次对话中悄悄推翻 |
| 可扩展机制 | 功法、灵力池、能力、持续状态、克制关系、修炼条件 | 用引擎支持的规则构件提案、验收、登记后生效 |
| 具体情境裁定 | 湿衣能否缓解火伤、两种护盾如何叠加 | 优先复用既有规则；必要时保存范围明确的解释性先例 |

边界看影响，不只看名称。新增一本功法通常是内容扩展；改变所有人修炼消耗或复活代价就是世界基本法则变更。名为“新功法”却能重写所有能力优先级，同样不能自动通过。

## 触发与处理流程

`玩家意图/世界生成事件 → 查询既有规则和裁定先例 → 发现缺口 → AI 提出最小规则补全 → 静态检查与样例演算 → 确定生效范围和时机 → 同一事务登记版本及事件 → 按已激活规则裁定 → 小说正文`

已经有规则时必须复用，不能每次提问重新生成。规则身份依据机制、对象与范围，不依赖玩家恰好用了哪种说法。查询不到也不等于不存在；规则检索不完整时，不能把已有约束当作空白重建。

提案至少包括：规则 ID、版本、所属世界、规则类别、依赖版本、适用对象与条件、输入与单位、来源与代价、效果与期限、叠加方式、结算阶段、随机来源、生效事件、事实依据和边界用例。描述性文本和可执行规则分开保存；“斩断一切”“无视境界”等名字或小说措辞不能直接成为执行权限。

只有支持的构件才能自动落地。可考虑的最小构件为：有界属性/资源池、带条件的资源转移、能力与标签、持续状态、有限目标选择、受限公式和引擎随机检定。禁止任意 Python/JavaScript、文件操作、网络请求，以及模型指定未授权数据库字段。

## 例一：新功法与灵力

玩家找到《引露诀》，初始剧本只写了“可从晨露凝聚水灵气”。首次研习前，可以补全：哪些角色能学习、何种环境可练、修习耗时、灵力从何而来、储存上限、每次术法的消耗、熟练度如何影响效率。

数值由世界已有的境界尺度和效果预算约束，不由模型根据名字随意放大。没有灵力不能照常施法；环境灵气作为来源需要明确规则。消耗灵力产生的效果不能再无限回补同一份灵力。

如果旧存档根本没有灵力字段，新增资源池还需要有版本的初始化方案：依据什么已有事实确定容量和当前值、是否仅把原有抽象能力显式化、如何避免额外赠送力量。不能简单给所有角色填满一百点，也不能把灵力当成生命的别名混算。无法证明初始化与原有事实相容时，不自动迁移；可以先停在研习或感知阶段，或将机制留给后续兼容版本。

成功激活后，同一功法的消耗、边界与成长方式必须持续有效，跨回合和重启后复用。原先没有明确的细节可以逐步揭示；已经展示过的能力事实不得随意否认。

## 例二：随机超能力

可以在觉醒、奇遇或实验事件中生成世界题材允许的新能力。先由引擎依据已登记的触发条件和随机结果确定强度档位、代价与限制预算，AI 再在这个范围内提出机制和表现。

例如“短暂交换两个物件的位置”，要定义目标类别、数量、距离、重量或力量差限制、视线要求、消耗、恢复条件，以及受结界或他人控制的物件如何抵抗。不能只写一句“空间能力”便允许交换山峰、敌人心脏或世界法则。

未接受的候选能力不算已获得。觉醒、能力定义和随机结果一旦提交就持久保存；重试请求、换一种问法、重启或复活不能免费重抽。若需要重修、变异或洗练，应由另一条明确的世界规则决定。

## 例三：能力冲突、优先级与克制

不使用“功法名字更霸气”“描述里写了绝对”“角色是主角”等作为优先级。AI 也不能提交任意大的 priority 来压过全部效果。

先建立公共结算阶段，例如：资格与目标检查 → 承诺本次合法代价 → 前置限制/打断 → 能力相互作用 → 按规则结算影响 → 有界后续触发。阶段内部的顺序或同时结算方式由世界规则事先确定；具体阶段顺序是待实现的设计方案，不是已经运行的战斗引擎。

克制要是有条件的关系，而不是看到“水”就必定战胜“火”。可以考虑作用对象、力量规模、强度、环境、持续时间、穿透和抗性等已定义量。水雾也许能减弱普通火焰，却不能仅凭元素名字熄灭高境界真火。克制可以降低效率、提高消耗或改变表现，不必总是判为完全无效。

“无视防御的剑”与“绝对防御的盾”需要先解释可执行语义：穿透哪类防御、在哪个强度范围内、防护针对什么伤害、各有什么限制。若两个已登记效果仍直接矛盾，采用已有公共冲突规则；不能让模型临时宣布其中一个“更绝对”。

组合测试应覆盖顺序交换、相同效果叠加、持续时间、双方同时触发、反射与再次反射等情况。结算依赖环、无限触发和无限资源回路必须被拒绝或由固定上限终止。元素克制图本身可以循环（甲克乙、乙克丙、丙克甲）；这与会让程序无限执行的依赖环不同。

## 生效时机与公平性

发现一本新功法时，在首次学习或施放前补全其规则。生成一个敌人的特殊能力时，先确定能力与代价，再让它参与裁定；不能看到玩家选了火攻，才给敌人编出此前没有依据的火焰免疫。

玩家可见知识与世界真实规则分开。隐藏弱点可以存在、可以被探索，但应有预先登记的事实或既定生成规则；未知不等于裁判可以按期待的胜负随意补写。

每段已经承诺的交锋固定使用一份规则版本和已确定的随机结果。可以依据其中已有的通用语义解决新组合；解释性先例不能增加新能力、改代价或重新抽签。需要实质性新规则时，不能回溯改变这段交锋。无法按旧规则可靠裁定，就停在执行前；候选规则在下一次合法边界验收生效。

“先补规则再裁定”不是允许在玩家已经选择后量身定做输赢。提案必须与既有事实和公共规则相容，对同条件的玩家及 NPC 一致适用，且不读取尚未产生的胜负随机结果来设计规则。

## 版本、持久化与故障处理

规则按世界隔离；同一世界的通用规则由玩家和 NPC 共同遵守，特殊例外必须有明确能力依据。某玩家的奇遇不能改动所有其他世界。功法实例和事件记录引用具体规则版本，已提交版本不可原地覆盖。

建议生命周期：候选 → 验收通过 → 激活；冲突或缺少引擎构件的提案留在候选/拒绝状态，不展示为已生效。并发提案依据版本与唯一身份去重，不能双重发放能力或重复初始化资源。

规则注册、必要状态初始化、随机结果与第一次事件效果必须原子提交。失败不扣资源、不留半个能力。后续修正规则要保留旧版本；撤销候选或停用未来规则不能删除已发生的历史。确需修复错误存档时另做可审计迁移或补偿，不把回滚规则版本冒充成回滚整个世界。

自动检查包括结构/引用/单位、权限、范围、资源来源、公式边界、依赖和触发上限、与已有裁定的冲突，以及固定边界样例。模型自称“合理”或另一个模型给高分不能替代这些检查。新机制的语义合理性仍需真实对局与人工评估，不能承诺任意规则都能自动证明正确。

## 玩家看到什么

规则补全、版本和验收流程留在后台。玩家研习时可以看到：

> 瓷碗边缘的露水轻轻一颤，聚成了细小的水珠。你试着再牵引一缕，丹田却传来一阵空落；那颗水珠随即散开，重新洇湿了碗沿。

这段描写必须对应已经执行的练习与灵力消耗。不能用小说掩盖失败，也不展示“热更新规则成功”。玩家主动问功法限制、消耗或为何被克制时，应解释已知规律，提供可理解、可预测的依据；“隐藏机制”不能成为永远不解释裁定的理由。

## 最小实现验收

先验证一种资源池、一部运行时生成的功法、两种能力相互作用，沿用现有 SQLite、事务与叙述流程，不扩展大规模战斗或装备系统。

1. 剧本无专用功法 ID，首次研习能提出、验收、登记规则并执行；失败则规则和资源都不半途落库。
2. 同样的问题换一种说法、进程重启后仍使用相同版本与代价，不重新随机创造。
3. 生成规则不能更改复活、权限、世界上限，也不能让玩家通过“给我无敌能力”直接授予自己效果。
4. 水/火、穿透/护盾、反射/反射有可重现裁定；拒绝非法结算环，允许合法的循环克制关系。
5. 战斗中发现新组合不按胜负需要补规则，不修改已承诺交锋的版本和随机结果。
6. 现有存档引入灵力必须通过初始化与一致性检查，不重置成长、不凭空赠送资源。
7. 正文、规则记录与实际状态一致；能通过主动询问了解已知限制。

本轮仅补充设计；现有运行时尚不支持上述动态规则注册、版本激活或机制迁移。
